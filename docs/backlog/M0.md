## T-02 · App skeleton with module boundaries

**Type** Task · **Milestone** M0 · **Workstream** A · Platform · **Priority** Must · **Size** M
**Depends on** {{T-01}} · **Blocks** everything with code

### Context
The architecture is a modular monolith. The boundaries only hold if tooling enforces them from the first commit.

### Scope
- In: Next.js app, TypeScript config, module folders, shared stubs, lint, formatter, test runners, npm scripts.
- Out: database (T-03), deploys (T-04), styling (T-06).

### Implementation notes
- Check the current stable versions on day one and pin them exactly (no `^`): Next.js (App Router, `src/` dir), React, TypeScript, ESLint, Prettier, Vitest, Playwright, Zod. If Next.js renamed `middleware` to `proxy`, use the new name everywhere and note it in `docs/explanation/architecture.md`.
- `.nvmrc` with Node 22.
- `tsconfig.json`: `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, path alias `@/*` → `src/*`.
- Create `src/modules/<module>/index.ts` for the ten modules, each exporting nothing yet.
- Boundary rule (ESLint, `no-restricted-imports` or `eslint-plugin-boundaries`): importing `@/modules/<x>/<anything but index>` from outside module `<x>` is an error. Modules may import `@/shared/*` and `@/ui/*`.
- `src/shared/`: `errors.ts` (DomainError, codes), `result.ts` (`Result<T>`), and `actions.ts` with `authedAction` typed but with session and transaction stubbed until T-03 and S-01.
- npm scripts: `dev`, `build`, `start`, `lint`, `typecheck`, `test`, `test:int`, `test:e2e`, `db:generate`, `db:migrate`, `format`.
- `vitest.config.ts` (unit: `*.test.ts`; integration project: `*.int.test.ts`), `playwright.config.ts` (mobile Chrome viewport 390×844 plus desktop).
- A placeholder home page saying "Pesqueiro.GG" in the default font.

### Acceptance criteria
- [ ] Given a fresh clone, when I run `npm ci && npm run build`, then it builds with no warnings about the TypeScript config.
- [ ] Given a file in `src/modules/social` that imports `@/modules/logbook/commands`, when I run `npm run lint`, then it fails naming the boundary rule.
- [ ] Given the same import through `@/modules/logbook`, then lint passes.
- [ ] Given `npm test` and `npm run test:e2e`, then one sample unit test and one smoke test (home page loads) pass.
- [ ] Given `package.json`, then every dependency is pinned to an exact version.

### Tests
- Unit: sample test for `Result` helpers.
- Lint fixture: a deliberately bad import in a test-only file that CI expects to fail (or a unit test running ESLint programmatically on a fixture).
- E2E: home page smoke test.

## T-03 · Databases, migrations and the app database account

**Type** Task · **Milestone** M0 · **Workstream** A · Platform · **Priority** Must · **Size** M
**Depends on** {{T-02}} · **Blocks** every item that stores data

### Context
The browser never talks to the database. The server connects through Supabase's transaction pooler as its own account, `app_server`, which the XP ledger later restricts to insert-only. Row-level security stays on as a backstop so the public browser key can read nothing.

### Scope
- In: Supabase projects, local Supabase, Drizzle setup, the `app_server` role, the RLS helper, connection handling.
- Out: application tables (each item adds its own).

### Implementation notes
- Projects (region São Paulo, `sa-east-1`): `pesqueiro-dev` and `pesqueiro-prod` in the team's Supabase organization (owner: Amanda; Kauê and Guma as Developers, so the free-plan limit of two projects per Owner or Admin isn't exceeded). `pesqueiro-demo` is created later, before the demo seed (S-44), in a teammate's account with a free slot. Local: `supabase init` and `supabase start`.
- First migration (SQL, run as the owner):
  - `create role app_server login password '<from secret>' noinherit;`
  - grant usage on schema `public`, and default privileges so future tables get `select, insert, update, delete` for `app_server`.
  - `create function app_enable_access(t regclass)`: enables RLS on `t` and creates `policy app_server_all on t for all to app_server using (true) with check (true)`. Every later migration calls it for its tables.
  - `pgcrypto` extension if not present.
- Check on day one that Supavisor accepts the custom role (`app_server.<project-ref>` as the user). If it doesn't, fall back to a dedicated database user documented in `docs/reference/data-model.md`.
- Drizzle: `drizzle.config.ts` reads `DATABASE_MIGRATION_URL` (direct connection, owner) for migrations; `src/shared/db/client.ts` uses `postgres` (postgres.js) with `DATABASE_URL` (pooler port 6543, `app_server`), `prepare: false`, `max: 1` per serverless instance.
- `withTransaction(fn)` in `src/shared/db/` wraps `db.transaction`, sets `statement_timeout = '5s'` locally, and passes `tx`.
- Environment variables (documented in `.env.example`): `DATABASE_URL`, `DATABASE_MIGRATION_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (server only; storage and auth admin), `APP_ENV` (`local`, `dev`, `demo`, `production`).
- Storage bucket `media` (public read, no listing; writes only through the server with the service role).

### Acceptance criteria
- [ ] Given a fresh clone, when I run `supabase start && npm run db:migrate`, then the migration applies cleanly and `app_server` exists.
- [ ] Given a table created through `app_enable_access`, when I query it with the public anon key through Supabase's REST API, then I get no rows.
- [ ] Given the same table, when the app queries it as `app_server` through the pooler, then reads and writes work.
- [ ] Given the dev and production projects (and demo, once created), then each has the migration applied and its connection strings stored in the deploy secrets (T-04), never in the repo.

### Tests
- Integration: create a temporary table with `app_enable_access`, assert anon REST gets nothing and `app_server` can read and write.

## T-04 · Delivery pipeline: feature → dev → main

**Type** Task · **Milestone** M0 · **Workstream** A · Platform · **Priority** Must · **Size** M
**Depends on** {{T-02}}, {{T-03}} · **Blocks** {{S-37}}

### Context
Every change goes through a pull request into `dev`, is tested on the Dev environment, and reaches demo and production only through `dev → main`. Migrations must run before the code that needs them is deployed.

### Scope
- In: GitHub Actions, Vercel projects, environment variables, branch protection, migration-then-deploy ordering.
- Out: monitoring (T-05).

### Implementation notes
- `.github/workflows/ci.yml` on pull requests into `dev` and `main`: `npm ci`, lint, typecheck, unit tests, `supabase/setup-cli` + `supabase start`, `npm run db:migrate`, integration tests, `npm run build`, Playwright (upload the report on failure). Name the job `ci` so branch protection can require it.
- `.github/workflows/deploy.yml`:
  - on push to `dev`: migrate the dev database (`DEV_DATABASE_MIGRATION_URL` secret), then `vercel deploy` the `dev` branch to the Dev environment with the Vercel CLI (`VERCEL_TOKEN`, org and project IDs as secrets).
  - on push to `main`: migrate production (and demo, once it exists), then `vercel deploy --prod`. Make the demo steps skip cleanly when `DEMO_DATABASE_MIGRATION_URL` is unset.
  - Turn off Vercel's automatic Git deploys for `dev` and `main` so deploys always follow migrations. Keep automatic previews for pull requests (they use the dev database).
- Vercel projects: `pesqueiro` (production) and, once its database exists, `pesqueiro-demo` (until then, `main` deploys production only). Dev runs as `pesqueiro`'s preview for branch `dev` with branch-scoped variables. If the free plan doesn't allow branch-scoped variables, create a third project `pesqueiro-dev` and note it in `docs/reference/environments.md`.
- Region `gru1` in `vercel.json`.
- Branch protection: `dev` requires a PR and green `ci`; `main` requires a PR, green `ci` and one approval; no force pushes on either. While building, set `dev` as the repo's default branch so new PRs target it; switch back to `main` in {{S-47}}.
- `docs/reference/environments.md`: the flow, environments, secrets list, how to hotfix (branch from `main`, PR into `main`, then merge `main` back into `dev`).

### Acceptance criteria
- [ ] Given a PR into `dev` with a failing test, then `ci` fails and merging is blocked.
- [ ] Given a green PR merged into `dev`, then the dev database is migrated and the Dev environment serves the new commit within 10 minutes.
- [ ] Given a `dev → main` PR merged with one approval, then demo and production are migrated and deployed with the same commit.
- [ ] Given a direct push to `main`, then GitHub rejects it.

### Tests
- The pipeline itself: one deliberately failing PR (closed after), one real PR through to production. Record both in this issue.

## T-05 · Observability base and Discord alerts

**Type** Task · **Milestone** M0 · **Workstream** A · Platform · **Priority** Must · **Size** S · **Labels** privacy
**Depends on** {{T-04}} · **Blocks** {{S-34}}

### Context
Errors, traces and logs live in Sentry, linked by one trace ID. Uptime checks hit `/api/health`. Alerts go to Discord: `#alerts` for demo and production, `#alerts-dev` for Dev. Personal data never leaves the server.

### Scope
- In: Sentry setup with scrubbing, logger and span helpers, the health route, uptime monitors, Discord routing.
- Out: the five alert targets (S-34), the daily-job heartbeat (S-27), AI spending (S-33).

### Implementation notes
- `@sentry/nextjs` with its instrumentation files. Options: `sendDefaultPii: false`; no Session Replay; `tracesSampleRate` 1.0 on local and dev, 0.2 on demo and production; `environment` from `APP_ENV`; `release` from `VERCEL_GIT_COMMIT_SHA`; logs enabled (`enableLogs`). If the free plan's log quota is too small, use Axiom from `log.ts` instead and note it in `docs/reference/observability.md`.
- `src/shared/observability/scrub.ts`: `beforeSend`, `beforeSendTransaction` and `beforeBreadcrumb` drop request bodies, cookies and headers except `user-agent`, and remove keys named `lat`, `lng`, `latitude`, `longitude`, `email`, `photo`, `body` anywhere in the payload. User context is `{ id }` only.
- `log.ts`: `log.info|warn|error(event: string, fields: Record<string, unknown>)` → Sentry logger, fields scrubbed the same way. `span.ts`: `withSpan(name, fn)`.
- `src/app/api/health/route.ts`: `select 1` with a 2-second timeout; returns `{ status: 'ok', commit, env, time }` with 200, or 503 and `status: 'degraded'` on failure; `Cache-Control: no-store`; no auth.
- Uptime: UptimeRobot (or Better Stack) monitors for demo and production `/api/health`, every 5 minutes, alerting a Discord webhook in `#alerts`. These requests also keep the free databases from pausing.
- Discord: create `#alerts-dev`. Connect Sentry's Discord integration; alert rule "a new issue is created" → `#alerts` for environments demo and production, `#alerts-dev` for dev. Store webhook URLs only in the tools and in Vercel environment variables.
- A temporary `/api/debug/boom` route that throws, enabled only when `APP_ENV` is `local` or `dev`.

### Acceptance criteria
- [ ] Given `/api/health` on each environment, then it returns 200 with the deployed commit.
- [ ] Given a call to `/api/debug/boom` on Dev, then an issue appears in Sentry and a message in `#alerts-dev` within 5 minutes.
- [ ] Given an error whose context includes `{ lat: -23.1, email: 'x@y.z' }`, then neither value appears anywhere in the Sentry event.
- [ ] Given the uptime monitor paused against a wrong URL, then `#alerts` gets an outage message.
- [ ] Given `/api/debug/boom` on production, then it returns 404.

### Tests
- Unit: `scrub` removes nested coordinate and email keys from events, breadcrumbs and log fields.
- Integration: health route returns 503 when the database URL is wrong.

## T-06 · Design tokens and app shell

**Type** Task · **Milestone** M0 · **Workstream** C · Social · **Priority** Must · **Size** M
**Depends on** {{T-02}} · **Blocks** every UI item

### Context
The design system (source files in `design/`, summarized in `docs/reference/design-system.md`) defines colors for light and dark, two fonts, spacing, radii, shadows and 13 components. The app uses those tokens and nothing else.

### Scope
- In: tokens as CSS variables, Tailwind mapping, fonts, theme switching, primitives (`Button`, `Chip`, `Icon`, `Avatar`, `Logo`), the app shell and bottom bar.
- Out: domain components (`Sticker`, `CatchCard`, `LeaderboardRow` …) come with their items.

### Implementation notes
- `src/app/tokens.css`: every color token from `tokens.json` as `--<name>` under `:root` (light) and `[data-theme="dark"]`, plus `@media (prefers-color-scheme: dark)` for `:root:not([data-theme="light"])`. Spacing, radius, size and shadow tokens too.
- Tailwind (current major): map tokens in the theme config (`bg`, `surface`, `ink`, `water`, `bobber`, `gold`, `reed`, `paper`, rarity colors …) so components write `bg-surface text-ink`, never hex values.
- Fonts with `next/font/google`: Big Shoulders Display (700, 800, 900) as `--font-display`; Atkinson Hyperlegible (400, 700, italic) as `--font-body`.
- Theme: a `theme` cookie (`system`, `light`, `dark`) read on the server to set `data-theme` on `<html>` before paint; a switch in Settings (stub page).
- Icons: `lucide-react`, pinned to the version matching the design system (1.60.x); `src/ui/Icon.tsx` wraps it with the default size 20 and `aria-hidden` unless a label is passed.
- `src/ui/Logo.tsx`: the bobber mark and wordmark from the design system (`variant: 'full' | 'mark'`).
- `src/app/(app)/layout.tsx`: header (logo, bell placeholder), main column max 640 px, `BottomNav` with Feed, Álbum, Registrar (raised red button), Desafios, Perfil; safe-area padding; desktop ≥1024 px moves navigation to a side rail.
- Placeholder pages for each tab so navigation works.

### Acceptance criteria
- [ ] Given the app on a 390 px phone, then the bottom bar shows five destinations with the Log button raised in bobber red, and nothing scrolls sideways.
- [ ] Given the theme set to dark, then every placeholder screen uses dark tokens with no flash of the light theme on load.
- [ ] Given `grep -rE "#[0-9a-fA-F]{3,8}" src --include=*.tsx`, then no literal colors appear in components.
- [ ] Given keyboard navigation, then every nav item shows the focus ring.

### Tests
- E2E: navigate all five tabs on mobile viewport; toggle theme and reload.
- Unit: `Button` renders each variant with the right classes (snapshot is fine).

## T-07 · Portuguese and English from the first screen

**Type** Task · **Milestone** M0 · **Workstream** C · Social · **Priority** Must · **Size** S
**Depends on** {{T-02}} · **Blocks** every UI item

### Context
The interface ships in Portuguese and English. Retrofitting translation is expensive, so no string is ever hard-coded.

### Scope
- In: next-intl without locale routing, message files, formatters, a language switch, a CI check.
- Out: translating user content (never).

### Implementation notes
- next-intl configured "without i18n routing": `src/i18n/request.ts` picks the locale from the `NEXT_LOCALE` cookie, else `Accept-Language` (pt → `pt-BR`, everything else → `en`). After S-03, the profile's language writes the cookie.
- `messages/pt-BR.json` and `messages/en.json`, namespaced by area (`common`, `nav`, `auth`, `onboarding`, `groups`, `log`, `feed`, `album`, `ranking`, `challenges`, `notifications`, `settings`, `errors`).
- `src/shared/i18n/format.ts`: `formatWeight(grams, locale)` ("2,4 kg" / "2.4 kg", grams under 1 kg as "750 g"), `formatLength(mm, locale)` ("48 cm"), `formatNumber`, `formatDate(date, locale)` and `formatRelative` with `timeZone: 'America/Sao_Paulo'`.
- Error codes map to messages under `errors.*` (`errors.RATE_LIMITED` …).
- `scripts/check-i18n.mjs`: fails if a key exists in one file and not the other, or if a value is empty. Runs in `ci`.
- Language switch in Settings (stub) that sets the cookie and refreshes.

### Acceptance criteria
- [ ] Given a browser set to Portuguese, then the shell shows Portuguese labels; set to French, then English.
- [ ] Given the language switched in Settings, then every visible string changes after refresh.
- [ ] Given a key added only to `en.json`, then CI fails naming the key.
- [ ] Given `formatWeight(2400, 'pt-BR')`, then it returns "2,4 kg"; with `'en'`, "2.4 kg".

### Tests
- Unit: formatters in both locales, including dates near midnight in Brasília time.
- CI: the key check.
