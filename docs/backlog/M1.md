## T-08 · Species catalog: research and review

**Type** Task · **Milestone** M1 · **Workstream** B · Gamification · **Priority** Must · **Size** L
**Depends on** {{T-03}} · **Blocks** {{S-08}}, {{S-09}}, {{S-13}}, {{S-14}}

### Context
The album, rarity, XP and species ID all depend on a curated list of Brazilian species. Rarity comes from a public rubric (range, difficulty, stocking), never from conservation status. Protected species get a flag instead of a tier. See `docs/reference/xp-and-levels.md#rarity`.

### Scope
- In: the data, its table, an idempotent seed, review records.
- Out: regional rarity (later), closed-season calendars (out of scope).

### Implementation notes
- Table `species` in `catalog/schema.ts`: `id` (slug, e.g. `tucunare-acu`), `album_no` (int, unique, fixed forever once assigned), `scientific_name`, `name_pt`, `name_en`, `aliases_pt` (text[], regional names for search), `habitat` (`freshwater` | `marine` | `both`), `rarity_tier` (`comum` | `incomum` | `raro` | `epico`), `is_protected` (bool), `protection_note_pt`, `protection_note_en`, `sources` (text[]), `reviewed_by` (text), `reviewed_at`.
- Data in `src/modules/catalog/data/species.json`; `scripts/seed-catalog.ts` upserts by `id` and never changes an existing `album_no`.
- Rubric scores per species (range 0–2, difficulty 0–2, stocking −1–0) stored in the JSON for transparency; the tier is derived: 0–1 comum, 2 incomum, 3 raro, 4+ épico. Document it in `docs/explanation/gamification.md`.
- Sources: FishBase for distribution; Brazil's official list of threatened species (Ministério do Meio Ambiente) for `is_protected`. AI may draft entries; a person checks each one and fills `reviewed_by`.
- Album numbering: group by habitat and family, then alphabetical by `name_pt`; assign once.
- `catalog` queries: `listSpecies(locale)`, `getSpecies(id)`, `searchSpecies(q, locale)` (matches name, aliases, scientific name, accent-insensitive with `unaccent`).

### Acceptance criteria
- [ ] Given the seed run twice, then the table has the same rows and the same `album_no` values.
- [ ] Given at least 40 species by 12 Nov and 60 by the beta, then each has both names, scientific name, tier, protected flag, a source and a reviewer.
- [ ] Given `searchSpecies('tucunare', 'pt-BR')`, then it finds "Tucunaré-açu" and other tucunarés.
- [ ] Given a species on the threatened list, then `is_protected` is true and its tier is ignored by the XP rules.

### Tests
- Unit: tier derivation from rubric scores; JSON schema validation (Zod) of the data file in CI.
- Integration: seed idempotency.

## S-01 · Sign in with Google

**Type** Story · **Milestone** M1 · **Workstream** A · Platform · **Priority** Must · **Size** S · **Journey** J1

### Story
As an angler invited by a friend, I want to sign in with Google, so that I can join without waiting for an email.

### Context
Google login is the main entry for groups invited from WhatsApp: no email delivery, no password. Supabase Auth handles OAuth; our server only reads the session.

### Scope
- In: Google provider setup per environment, the callback route, session refresh, redirect back to where the person was going.
- Out: email and password (S-02), profile setup (S-03).

### Implementation notes
- Google Cloud: one OAuth client (web) with redirect URIs for local, Dev, demo and production Supabase callback URLs; consent screen with only `email` and `profile` scopes (no Google verification needed).
- Supabase: enable the Google provider in each project; set Site URL and allowed redirect URLs per environment.
- `@supabase/ssr`: `src/shared/auth/server.ts` (`getSession()`, `requireViewer()`), `src/shared/auth/browser.ts` (only for `signInWithOAuth`).
- `/login` page: "Continuar com Google" primary button; email option links to S-02.
- `src/app/auth/callback/route.ts`: `exchangeCodeForSession`, then redirect to `next` (validated: same-origin path only) or `/feed`.
- The proxy/middleware refreshes the session cookie on each request and redirects signed-out users from app routes to `/login?next=<path>`. Public routes: `/`, `/login`, `/signup`, `/auth/*`, `/invite/*`, `/p/*`, `/u/*`, `/terms`, `/privacy`, `/api/health`.
- After sign-in, if the user has no profile, redirect to `/onboarding?next=…` (S-03).
- `authedAction` now resolves the real viewer.
- i18n namespace `auth`.

### Acceptance criteria
- [ ] Given a signed-out person on `/invite/ABC123`, when they choose Google and approve, then they come back to `/invite/ABC123` (or onboarding first if new).
- [ ] Given a signed-in person, when they reopen the app a week later, then they're still signed in.
- [ ] Given `next=https://evil.example`, then the callback ignores it and goes to `/feed`.
- [ ] Given a signed-out request to `/feed`, then it redirects to `/login?next=/feed`.

### Tests

- E2E: Google can't run in CI; use Supabase local email sign-in for the journey and test the callback route's redirect logic with a mocked exchange.

## S-02 · Sign up with email and password

**Type** Story · **Milestone** M1 · **Workstream** A · Platform · **Priority** Must · **Size** S · **Journey** J1

### Story
As an angler without a Google account, I want to sign up with my email, so that I can still join.

### Context
Supabase's built-in email sends only a few messages an hour. Emails go through Resend instead. **Resend only delivers to arbitrary addresses from a verified domain**, so this item needs the team's domain; until then, email sign-up works for team addresses only and the beta relies on Google.

### Scope
- In: sign-up, confirmation, sign-in, password reset, Resend as SMTP, bilingual email templates.
- Out: magic links, phone login.

### Implementation notes
- Resend: verify the domain (SPF and DKIM records), create an SMTP key, set it as custom SMTP in each Supabase project; sender `Pesqueiro.GG <nao-responda@<domain>>`.
- Email templates (confirm sign-up, reset password) in Supabase, bilingual (Portuguese first, English below), linking to `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=…`.
- `src/app/auth/confirm/route.ts`: `verifyOtp({ token_hash, type })`, then redirect (`recovery` → `/reset-password`).
- Pages: `/signup` (email, password ≥ 10 characters, show/hide), `/login` email form, `/forgot-password`, `/reset-password`.
- Same neutral message whether or not the email already exists ("Se este e-mail puder ser usado, enviamos um link"), so nobody can probe which emails have accounts.
- Supabase's own auth rate limits stay on; our forms disable the button while submitting.
- i18n namespace `auth`.

### Acceptance criteria
- [ ] Given a new email, when I sign up, then I get the confirmation email from the Pesqueiro.GG sender within a minute, and the link signs me in.
- [ ] Given an existing email, when I sign up again, then I see the same neutral message.
- [ ] Given "forgot password", then the reset email's link opens `/reset-password` and the new password works.
- [ ] Given a weak password, then the form explains the rule in the person's language.

### Tests
- E2E (local Supabase with Inbucket for emails): sign up, confirm through the captured email, sign in, reset password.

### Story
As a group captain, I want to create a group and get an invite link, so that I can bring my fishing friends in from WhatsApp.

### Context
Groups are the product's unit: small circles of people who fish together, with their own feed, ranking and challenges. The captain brings in 5–15 people with one link.

### Scope

- [ ] Given "Convidar" on a phone, then the native share sheet opens with the text and link.

## S-06 · Leave a group or remove a member

**Type** Story · **Milestone** M1 · **Workstream** C · Social · **Priority** Must · **Size** S
**Depends on** {{S-05}} · **Blocks** nothing

### Story
As a member, I want to leave a group, and as an admin, I want to remove a member, so that groups stay among people who fish together.

### Scope
- In: leave, remove, admin succession, what happens to the person's posts in that group.
- Out: banning (a removed person can rejoin if they still have a valid link; the admin can regenerate it).

### Implementation notes
- Commands: `groups.leaveGroup({ groupId })`, `groups.removeMember({ groupId, userId })` (admin only; can't remove admins).
- When the last admin leaves and members remain, promote the longest-standing member to admin. When the last member leaves, the group stays but is empty (no deletion).
- On leave or removal: delete that person's `post_groups` rows for the group (their posts leave the group's feed), emit `MemberLeft` and `AudienceChanged` for those posts.
- Rankings only count current members (S-16 joins `group_members`).
- UI: group page → members list (S-04's page) with "Remover" for admins; "Sair do grupo" in the group menu with an in-page confirmation step (no `confirm()` dialogs).

### Acceptance criteria
- [ ] Given a member who leaves, then the group disappears from their feed tabs and their posts disappear from the group's feed.
- [ ] Given the only admin leaving a group with members, then the longest-standing member becomes admin.
- [ ] Given an admin removing another admin, then it fails with FORBIDDEN.

### Tests
- Integration: leave, remove, succession, posts removed from the group's audience.

## S-07 · Upload catch photos safely

**Type** Story · **Milestone** M1 · **Workstream** A · Platform · **Priority** Must · **Size** M · **Journey** J2 · **Labels** privacy
**Depends on** {{T-03}}, {{T-05}} · **Blocks** {{S-08}}, {{S-09}}, {{S-22}}, {{S-23}}

### Story
As an angler, I want my photos uploaded fast and without hidden location data, so that sharing a catch never reveals my spot.

### Context
Phone cameras embed GPS in photos. The server never trusts an upload: it re-encodes everything, which drops all metadata. A perceptual hash lets official challenges spot the same photo on two accounts, even resized.

### Scope
- In: browser resize, upload route, server checks, WebP variants, perceptual hash, `media` table, image URLs.
- Out: video (won't have), cleanup of unattached files (scheduled in S-27's daily job, function written here).

### Implementation notes
- Browser: `src/modules/media/ui/compress.ts` draws the file into a canvas, longest side ≤ 2048 px, exports JPEG at 0.85. This also converts HEIC where the browser can decode it; otherwise show "Formato não suportado, tente um print da foto".
- `POST /api/media` (route handler, multipart, one file): signed in; rate limit 60 per day; reject over 4 MB; `sharp(buffer).metadata()` must report jpeg, png or webp, else 400.
- Processing with sharp: `.rotate()` first (applies EXIF orientation), then for widths 1600, 800, 320: `.resize({ width, withoutEnlargement: true }).webp({ quality: 80 })`. Sharp drops metadata by default; never call `withMetadata()`.
- Perceptual hash: 64-bit dHash (grayscale, 9×8, compare neighbours) as 16 hex characters.
- Storage: bucket `media`, path `<random uuid>/<width>.webp` (no user id in the path), uploaded with the service role.
- Table `media` (`media/schema.ts`): `id`, `owner_id`, `path_prefix`, `width`, `height`, `bytes`, `phash`, `status` (`ready`), `attached_at` (null until a post uses it), `created_at`.
- Response: `{ id, urls: { 1600, 800, 320 } }`.
- `media.cleanupUnattached(olderThanHours = 24)`: deletes files and rows never attached.
- URL helper `mediaUrl(path, width)` and a `next/image` custom loader that picks the closest variant.
- Log `media.uploaded` with `{ userId, bytes, ms }`.

### Acceptance criteria
- [ ] Given a JPEG with GPS EXIF, when uploaded, then none of the stored variants has any EXIF, GPS or XMP data.
- [ ] Given a phone photo taken sideways, then the stored image is upright.
- [ ] Given a PDF renamed `.jpg`, then the upload is rejected.
- [ ] Given a 10 MB photo on a phone, then the browser shrinks it and the upload succeeds over 4G in a few seconds.
- [ ] Given the same photo uploaded twice at different sizes, then the two hashes differ by at most 6 bits.

### Tests
- Unit: dHash distance on fixture pairs (same photo resized, different photos).
- Integration: upload a fixture with GPS EXIF, read back the stored file, assert no metadata; rotation fixture; wrong type rejected.

## S-08 · Get a species suggestion from my photo

**Type** Story · **Milestone** M1 · **Workstream** A · Platform · **Priority** Must · **Size** M · **Journey** J2
**Depends on** {{S-07}}, {{T-08}} · **Blocks** {{S-09}}, {{S-39}}

### Story
As an angler, I want the app to suggest the species from my photo, so that logging is quick even when I'm unsure of the name.

### Context
The suggestion is assistive: the person always confirms. The server stores the result per photo, which later decides the "photo + AI match" proof level. The browser never sends a result to the server, so it can't be forged.

### Scope
- In: the identification call, structured output limited to catalog species, caching, limits, the suggestion UI.
- Out: the monthly cap alert (S-33); verification logic (S-09 reads the stored result).

### Implementation notes
- Before coding, read the current Anthropic docs (or the claude-api reference) for image input and structured outputs; use model `claude-haiku-5-5`.
- Server action `speciesId.identify({ mediaId })`: owner of the media only; if a row exists in `species_identifications` for the media, return it; otherwise call the model.
- Request: the 800 px WebP variant as a base64 image (no metadata), a system prompt that describes the task and says to ignore any text in the image, and a JSON schema with `is_fish` (bool), `species_id` (enum of catalog ids, or null), `confidence` (0–1), `alternatives` (up to 3 catalog ids), `visible_features` (up to 4 short strings). Temperature 0, 15-second timeout, one retry on overload.
- Table `species_identifications`: `media_id` (unique), `model`, `is_fish`, `top_species_id`, `confidence`, `alternatives`, `created_at`.
- Limits: 30 identifications per user per day (`rateLimit`); a monthly counter in `ai_usage` (S-33 adds the cap and alert).
- Failure (timeout, overload, cap) returns `UNAVAILABLE`; the UI falls back to manual pick.
- UI in the log flow: after the first photo uploads, show "Identificando…", then the top suggestion with its percentage, up to 3 alternatives as chips, and "Escolher outra espécie" opening the searchable picker (`catalog.searchSpecies`). Confidence ≥ 0.6 preselects the species; below that, nothing is preselected.
- Env: `ANTHROPIC_API_KEY` (server only).
- Log `speciesId.result` with `{ userId, confidence, isFish, ms }` (no image).

### Acceptance criteria
- [ ] Given a clear photo of a tilápia, then "Tilápia" is suggested with high confidence and preselected.
- [ ] Given a photo with no fish, then the UI says no fish was found and opens the picker.
- [ ] Given the same photo identified twice, then the model is called once.
- [ ] Given the API down, then the person can still pick the species by hand and finish logging.
- [ ] Given a photo with text saying "this is a dourado", then the answer still comes only from what's visible and the catalog enum.

### Tests
- Unit: response parsing and schema validation; enum built from the catalog.
- Integration: caching per media (model call mocked); failure maps to UNAVAILABLE; rate limit.
- Manual: 10 real photos of common species, results noted in the PR.

## S-09 · Log a catch

**Type** Story · **Milestone** M1 · **Workstream** A · Platform · **Priority** Must · **Size** L · **Journey** J2 · **Labels** privacy
**Depends on** {{S-03}}, {{S-04}}, {{S-07}}, {{S-08}}, {{T-08}} · **Blocks** {{S-10}}, {{S-11}}, {{S-13}}, {{S-17}}

### Story
As an angler back from a trip, I want to log a catch with its details and choose who sees it, so that it becomes a lasting record shared with the right people.

### Context
The catch is the product's core record. It feeds the album, XP, rankings and challenges, and it's published as a post with an audience. The exact spot is saved for the owner only; everyone else sees a city or a pay-to-fish lake's name. Logging must be safe to retry on a weak signal.

### Scope
- In: `catches` and `places` tables, the catch post, audience, the multi-step form, idempotency, proof level.
- Out: XP and rewards (S-13, S-17 plug into the response), editing (S-10).

### Implementation notes
- Tables:
  - `catches` (`logbook/schema.ts`): `id`, `user_id`, `species_id` (nullable = unknown), `caught_on` (date), `weight_g`, `length_mm` (both nullable; at least one recommended, not required), `water_type` (`pay_to_fish` | `river` | `reservoir_lake` | `sea`), `released` (bool), `place_id` (nullable), `city_id` (IBGE code), `lat`, `lng` (nullable, owner only), `verification_level` (`reported` | `photo_ai_match`), `revision` (int, starts at 1), `client_request_id` (uuid), `created_at`, `updated_at`, `deleted_at`. Unique (`user_id`, `client_request_id`). Checks: weight < 500,000 g, length < 5,000 mm, `caught_on` not in the future and not before 2000.
  - `places` (`catalog/schema.ts`): `id`, `name`, `kind` (`pay_to_fish`), `city_id`, `state`, `lat`, `lng`, `created_by`, `created_at`; unique on lower(name) + city.
  - Posts come from the `social` module (`social.createCatchPost(tx, { catchId, authorId, groupIds, isPublic, mediaIds, story })`), which writes `posts` (`kind = 'catch'`, `catch_id` unique), `post_groups` (with `post_created_at` copied) and `post_media`, and marks media attached. If `social` isn't ready, implement that function in this item inside `social`.
- Command `logbook.logCatch(input)` (the usual action, `tx`, rate limit 20 per day):
  1. Insert the catch; on unique conflict for the request id, return the existing catch and post instead (idempotent).
  2. Verify every chosen group with `groups.isMember`; else `FORBIDDEN`.
  3. Compute `verification_level`: `photo_ai_match` when the first photo's stored identification has `top_species_id = species_id` and `confidence ≥ 0.6`.
  4. `social.createCatchPost(...)`.
  5. `emit(tx, { type: 'CatchChanged', catchId, userId, revision: 1 })`.
  6. Return `{ catchId, postId, rewards: null }` (S-13 fills rewards).
- Types: `OwnCatch` (all fields) for the owner, `PublicCatch` (no `lat`, `lng`, `client_request_id`) for everyone else, built by separate mappers in `logbook/queries.ts`.
- Form `/log`, five steps on one page with a progress bar:
  1. Photos: 1–4, the first starts identification (S-08).
  2. Species: the suggestion or the picker; "Não sei a espécie" allowed.
  3. Details: weight (kg with decimals, stored as grams), length (cm, stored as mm), water type (4 big buttons), released or kept toggle, date (today by default, can't be future).
  4. Place: if water type is pay-to-fish, search `places` or add one (name and city); otherwise "Usar minha localização" (GPS → `catalog.nearestCity`, coordinates kept for the owner) or pick a city. Show "Os outros veem só a cidade".
  5. Audience and story: checkboxes for my groups (all checked by default), "Público" toggle (off by default), story ≤ 2,000 characters.
- `client_request_id`: a uuid created when the form opens and kept in `sessionStorage`, so retries and double taps reuse it.
- i18n namespace `log`.

### Acceptance criteria
- [ ] Given the form completed with a photo, then the catch appears in my groups' feeds with the city or lake name only.
- [ ] Given a double tap on "Registrar", or a retry after a timeout, then exactly one catch exists.
- [ ] Given GPS used, then the owner's catch has coordinates and the `PublicCatch` returned to anyone else has no coordinate fields.
- [ ] Given a group I'm not in sent in the request, then the command fails with FORBIDDEN and nothing is saved.

## S-11 · See my group's feed

**Type** Story · **Milestone** M1 · **Workstream** C · Social · **Priority** Must · **Size** M · **Journey** J2 · **Labels** privacy
**Depends on** {{S-04}}, {{S-09}} · **Blocks** {{S-20}}, {{S-24}}, {{S-40}}

### Story
As a group member, I want a feed of my group's catches and posts, so that I keep up with my friends between trips.

### Context
Feeds are built when opened, behind an interface that returns post IDs first and fills them in second. Later, pre-built feed lists can replace the first step without touching anything else. See `docs/explanation/scaling.md` and the path to scale.

### Scope
- In: `TimelineSource`, `hydratePosts`, the group feed page, infinite scroll, the catch card.
- Out: merged "my groups" and public tabs (S-24), following feed (S-40).

### Implementation notes
- `social/timeline.ts`:
  ```ts
  type FeedRef = { scope: 'group'; groupId: string } | { scope: 'my_groups' } | { scope: 'public' } | { scope: 'following' } | { scope: 'author'; userId: string };
  interface TimelineSource { page(viewer: Viewer, feed: FeedRef, cursor?: string): Promise<{ ids: string[]; next?: string }> }
  ```
  `SqlTimelineSource` implements `group` here: `post_groups` where `group_id = $1` and `(post_created_at, post_id) < cursor`, ordered by both descending, limit 20, joined to `posts` to skip `hidden_at` and `deleted_at`.
- Cursor: base64url of `{"t": "<iso>", "id": "<uuid>"}`; treat it as opaque everywhere outside this file; reject malformed ones with VALIDATION.
- `social.hydratePosts(ids, viewer)`: one query each for posts, authors, `PublicCatch` data, media and the viewer's reaction; re-check `canViewPost(viewer, post)` and drop anything not visible; keep the order of `ids`.
- `canViewPost`: author, or `is_public`, or the viewer is a member of a group in `post_groups`.
- Route `/groups/[id]` (members only, else NOT_FOUND) renders the first page on the server; `GET /api/feed?scope=group&groupId=…&cursor=…` returns the next pages as JSON for the client hook `useFeed`.
- `CatchCard` from the design system (photo 4:3, author, group and time, species with rarity badge, facts line, place, story, reaction and comment buttons as placeholders until S-20/S-21).
- Index: `post_groups (group_id, post_created_at desc, post_id)`.
- Span `feed.page` with `{ scope, count }`; log duration for the p95 target.
- Empty state: "Ninguém registrou nada ainda. Que tal ser o primeiro?" with the Log button.

### Acceptance criteria
- [ ] Given a group with 45 posts, when I scroll, then I get 20, 20 and 5 with no duplicates or gaps.
- [ ] Given a new post created while I'm reading, then the next page doesn't repeat or skip anything.
- [ ] Given a post deleted after its ID was fetched, then it doesn't appear.
- [ ] Given a non-member requesting the feed, then they get 404.
- [ ] Given any card, then no coordinates are in the HTML or JSON sent to the browser.

### Tests
- Unit: cursor encode/decode; `canViewPost` truth table.
- Integration: pagination over seeded posts with ties in `created_at`; hidden and deleted posts skipped; non-member NOT_FOUND.
- E2E: part of J2.
