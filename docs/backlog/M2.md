# M2 · Gamification core (11–16 Nov)

Goal: logging a catch fills a sticker, adds XP, moves the group ranking and shows the reward screen. This is the product's heart and the demo's big moment.

## S-10 · Edit or delete my catch

**Type** Story · **Milestone** M2 · **Workstream** A · Platform · **Priority** Must · **Size** S · **Journey** J2
**Depends on** {{S-09}}, {{S-12}} · **Blocks** nothing (S-13 makes XP follow edits)

### Story
As an angler who made a mistake, I want to edit or delete a catch, so that my record and my XP stay right.

### Context
Edits change what the XP engine sees. Every edit emits `CatchChanged`, and S-13's replay recomputes the angler's XP from scratch, appending only the difference. Nothing is ever updated in place in the ledger.

### Scope
- In: edit form, update and delete commands, audience changes.
- Out: edit history UI.

### Implementation notes
- `/p/[id]/edit` reuses the S-09 form, prefilled; photos can be added, removed or reordered (at least one stays if there was one).
- Command `logbook.updateCatch({ catchId, … })` (owner only, tx): update fields, `revision = revision + 1`, `updated_at`; if audience changed, `social.setAudience(tx, postId, groupIds, isPublic)` (emits `AudienceChanged`); if the species changed, recompute `verification_level`; emit `CatchChanged { catchId, userId, revision }`.
- Command `logbook.deleteCatch({ catchId })` (owner only, tx): set `deleted_at` on the catch and its post, `revision + 1`, emit `PostDeleted` and `CatchChanged`. Media files are deleted after the response with `afterResponse(media.deleteForPost)`.
- `revision` is used for optimistic concurrency: the form sends the revision it loaded; if the stored one is higher, return CONFLICT ("Este registro mudou em outro aparelho. Recarregue.").
- In-page confirmation for delete (no browser dialogs).

### Acceptance criteria
- [ ] Given I change the species from tilápia to tucunaré, then the catch page and feed show tucunaré and (once S-13 is in) my XP reflects the change.
- [ ] Given I delete a catch, then it disappears from every feed and its page returns 404.
- [ ] Given someone else's catch, then edit and delete return NOT_FOUND.
- [ ] Given two devices editing the same catch, then the second save gets CONFLICT.

### Tests
- Integration: update increments revision and emits once; delete soft-deletes catch and post; concurrency conflict; non-owner NOT_FOUND.

## S-13 · Earn XP for fishing

**Type** Story · **Milestone** M2 · **Workstream** B · Gamification · **Priority** Must · **Size** L · **Journey** J2
**Depends on** {{S-09}}, {{T-08}} · **Blocks** {{S-14}}, {{S-15}}, {{S-16}}, {{S-17}}, {{S-18}}, {{S-27}}

### Story
As an angler, I want to earn XP for the fishing I log, so that my progress reflects variety and effort, not volume.

### Context
Every XP point is a row in an append-only ledger. On any catch change, the engine replays the angler's whole history through pure rule functions and appends only the difference. With 2–3 catches a month per person, a full replay costs almost nothing. See `docs/explanation/gamification.md`.

**Change from the system design:** ledger uniqueness uses a per-angler `replay_seq`, not the catch revision. With catch revisions, an award that moves from one catch to another (for example, a back-dated catch taking over the "new species" award) would need a reversal on an unchanged catch revision and break the unique key. See `docs/explanation/decisions/ADR-013-replay-sequence.md`; the docs already describe `replay_seq`.

### Scope
- In: seasons, the ledger, rules, replay, diff, projections (`user_progress`, `album_entries`), the hook into `logCatch`, `updateCatch` and `deleteCatch`, the rewards object.
- Out: challenge XP (S-27), badges table (S-19), screens (S-14 to S-17).

### Implementation notes
- Tables (`gamification/schema.ts`):
  - `seasons` (`id` like `2026-Q4`, `starts_at`, `ends_at` in Brasília time) seeded through 2027-Q4.
  - `xp_events` (`id`, `user_id`, `season_id` nullable, `rule`, `amount` int (negative allowed), `award_key`, `source_type` (`catch` | `challenge`), `source_id`, `replay_seq`, `ruleset_version`, `created_at`). Unique (`user_id`, `award_key`, `replay_seq`). Indexes (`user_id`, `season_id`), (`source_id`).
  - `user_progress` (`user_id` PK, `lifetime_xp`, `level`, `level_seen`, `species_count`, `water_types` text[], `replay_seq`, `updated_at`).
  - `album_entries` (`user_id`, `species_id`, `first_catch_id`, `first_caught_on`, `best_catch_id`, `best_weight_g`, `catch_count`, `seen_at` nullable; PK on user and species).
  - Migration: `revoke update, delete on xp_events from app_server`.
- Rules (`gamification/rules/*.ts`), each `(fact: CatchFact, ctx: ReplayContext) => Award[]`, `RULESET_VERSION = 1`:

  | Rule | Award key | XP |
  |---|---|---|
  | `catch_logged` | `catch:<id>:logged` | 20 for the first 3 catches of a fishing day, 10 for the 4th–6th, 0 after; 0 if logged more than 7 days after `caught_on`; 0 for a kept protected species |
  | `new_species` | `species:<speciesId>` (source = first catch of it) | 50 / 100 / 200 / 400 by tier; capped at 100 when `water_type = pay_to_fish`; 0 for protected or unknown species |
  | `new_water_type` | `water:<type>` (source = first catch in it) | 30 |
  | `milestone` | `milestone:<id>` (source = catch that reached it) | first catch 25; 5, 10, 25, 50 species: 100, 200, 400, 800; all four water types: 100 |

  Keys identify *what* was earned per angler, so an award moves between catches without double counting.
- `replay(catches, catalog, rules): Award[]`: catches sorted by `caught_on`, then `created_at`; deleted catches excluded; `ReplayContext` tracks species seen, water types seen and catches per day.
- `diff(desired: Award[], ledger: Map<awardKey, {sum, sourceId}>): Delta[]`: for each key, `desired.amount − ledger.sum` when non-zero; keys missing from desired get `−sum`.
- `applyCatchChange(tx, userId): Rewards`:
  1. `select … from user_progress where user_id = $1 for update` (insert the row first if missing). This lock serializes saves per angler.
  2. Load the angler's catches and current ledger sums by key.
  3. `replay`, `diff`; if no deltas, return empty rewards.
  4. `replay_seq = replay_seq + 1`; insert one `xp_events` row per delta with that `replay_seq`; `season_id` = season containing `caught_on` of the source catch, or null if the catch was logged more than 48 h after that season ended.
  5. Rebuild `user_progress` (lifetime XP from the ledger sum, level via S-15's `levelFor`, species count, water types) and `album_entries`.
  6. Return `Rewards { xpGained, newSpecies: [{ speciesId, tier, albumNo }], newWaterTypes, milestones, levelBefore, levelAfter, replaySeq }` from the positive deltas of this replay.
- Register `on('CatchChanged', (tx, e) => applyCatchChange(tx, e.userId))` in `gamification/events.ts`; `logCatch` and `updateCatch` return the rewards.
- `scripts/replay-all.ts` replays every angler (used after a rules change; bump `RULESET_VERSION`).
- Social actions never call the engine.

### Acceptance criteria
- [ ] Given my first tucunaré-açu (incomum) in a river, then I get 20 + 100 + 30 + 25 (first catch) = 175 XP.
- [ ] Given a stocked pintado (raro) in a pay-to-fish lake, then the species award is 100, not 200.
- [ ] Given 8 catches logged for the same day, then catch XP is 3×20 + 3×10 + 2×0.
- [ ] Given I change a catch's species from tilápia to tucunaré and back twice, then my XP equals logging it as tilápia once, and the ledger shows each change as a minus and a plus.
- [ ] Given I back-date a new tucunaré before my existing one, then the species award moves to the new catch with no change in total XP.
- [ ] Given two catches saved at the same moment with the same new species, then the species award is given once.
- [ ] Given `app_server`, when it tries `update` or `delete` on `xp_events`, then Postgres refuses.

### Tests
- Unit: every rule including caps, protected, unknown, late logging, daily diminishing returns; `diff` cases (add, remove, move); replay ordering ties.
- Integration: the scenarios above against Postgres, including the concurrent saves (two transactions in parallel, assert one species award) and the permission test.

## S-14 · Fill my species album

**Type** Story · **Milestone** M2 · **Workstream** B · Gamification · **Priority** Must · **Size** L · **Journey** J2
**Depends on** {{S-13}}, {{T-06}} · **Blocks** {{S-17}}, {{S-25}}, {{S-42}}

### Story
As an angler, I want an album where each new species fills a sticker, so that I have a reason to try new species and places.

### Context
The Álbum de Espécies is the product's signature screen: a paper sticker album with numbered slots. Comum and Incomum stickers are matte; Raro gets a sheen, Épico a sheen and a gold edge. Amanda is designing her own version; build the design system's `Sticker` first and swap the visuals when her design arrives.

### Scope
- In: `/album`, the album query, `Sticker` and album page components, the "Nova" flag, filters.
- Out: other people's albums (S-25), the drop animation (S-42).

### Implementation notes
- Query `gamification.getAlbum(userId, viewer, locale)`: all catalog species ordered by `album_no`, left-joined to `album_entries`; for filled slots, the photo of `best_catch_id` (heaviest, then longest, then first), only if the viewer can see that catch, otherwise the silhouette.
- `src/modules/gamification/ui/Sticker.tsx` and `AlbumPage.tsx` from the design system: paper background (`paper` token), grid `repeat(auto-fill, minmax(132px, 1fr))`, filled sticker (number, photo or silhouette, name in the display font, scientific name, `RarityBadge`, sheen for raro and épico), empty slot (dashed `paper-line` border, number, big "?", name).
- Header: "23 / 87 espécies", the `FishLine` progress, filters (all, filled, missing, by tier).
- "Nova" flag when `seen_at` is null; command `gamification.markAlbumSeen()` runs when the page opens (after render) and sets `seen_at` for all filled entries.
- Tapping a filled sticker opens the best catch's page; tapping an empty one shows the species name, habitat and "Ainda não pescado".
- Protected species show "Protegida" with the shield icon instead of a tier.
- i18n namespace `album`.

### Acceptance criteria
- [ ] Given my first tucunaré-açu, then its slot shows my photo, the Incomum badge and the "Nova" flag the first time I open the album.
- [ ] Given I reopen the album, then the flag is gone.
- [ ] Given a raro sticker, then it has the sheen; hovering on desktop moves it; with reduced motion it doesn't move.
- [ ] Given the catalog has 87 species, then the album shows 87 slots in `album_no` order.
- [ ] Given the page on a 360 px phone, then stickers fit at least two per row with no horizontal scroll.

### Tests
- Integration: `getAlbum` with filled, empty and protected species; best photo hidden from a viewer who can't see that catch.
- E2E: log a catch, open the album, see the filled sticker with "Nova".

## S-15 · Level up through the career

**Type** Story · **Milestone** M2 · **Workstream** B · Gamification · **Priority** Must · **Size** M · **Journey** J2
**Depends on** {{S-13}}, {{S-03}} · **Blocks** {{S-17}}, {{S-25}}

### Story
As an angler, I want to climb from Jovem Aprendiz to CEO dos Mares, so that my progress has a name my friends can laugh about.

### Context
Levels use lifetime XP. Titles keep the original app's corporate joke, in the form each person chose (masculine or feminine) and in English.

### Scope
- In: `levelFor`, titles, progress to next level, the promotion banner and its "seen" state.
- Out: the reward-screen animation (S-42).

### Implementation notes
- `levelFor(xp)`: the largest n with `50 × n × (n − 1) ≤ xp` (L1 0, L2 100, L3 300, L4 600, L5 1,000, L6 1,500, L7 2,100, L8 2,800, L9 3,600, L10 4,500). Above 10 the title stays "CEO dos Mares" and the number keeps growing.
- Titles in i18n under `career.<level>.m` and `career.<level>.f` (pt-BR) and `career.<level>` (en), as listed in `docs/reference/xp-and-levels.md#levels`.
- `careerTitle(level, titleForm, locale)` helper used everywhere a title shows.
- `FishLine` component (design system): progress from the current level's threshold to the next, label "Faltam 180 XP para Pescadora Sênior".
- `PromotionBanner`: shown when `user_progress.level > level_seen`, on the reward screen or at the top of the feed; "Aceitar o cargo" sets `level_seen = level` (`gamification.acknowledgeLevel()`).
- Profile header (own profile, S-25 for others): avatar, name, title, level number, FishLine.

### Acceptance criteria
- [ ] Given 99 XP, then I'm level 1 (Jovem Aprendiz); at 100, level 2 (Estagiário/Estagiária).
- [ ] Given title form feminine, then I see "Pescadora Plena" at level 4.
- [ ] Given I cross a level, then the banner shows once and not again after I accept.
- [ ] Given English, then the title reads "Mid-level Angler".

### Tests
- Unit: `levelFor` at every threshold and ±1; `careerTitle` for both forms and English.
- Integration: banner state after a level-up and after acknowledgment.

## S-16 · See my group's season ranking

**Type** Story · **Milestone** M2 · **Workstream** B · Gamification · **Priority** Must · **Size** M · **Journey** J2
**Depends on** {{S-13}}, {{S-11}} · **Blocks** {{S-17}}, {{S-18}}, {{S-27}}

### Story
As a group member, I want a season ranking for my group, so that the friendly rivalry has a scoreboard.

### Context
Seasons are calendar quarters. A group's ranking counts only XP from catches the group can see (shared with the group, or public), so every point is checkable by the people ranked. Your score can therefore differ between groups; the screen says why in one line.

### Scope
- In: the ranking query, the ranking tab, podium, my row, movement since last visit, season switcher.
- Out: challenge leaderboards (S-27).

### Implementation notes
- Query `gamification.groupSeasonRanking(groupId, seasonId)`:
  ```sql
  select m.user_id, coalesce(sum(e.amount), 0) as xp
  from group_members m
  left join xp_events e on e.user_id = m.user_id and e.season_id = $season and (
       (e.source_type = 'catch' and exists (
          select 1 from posts p where p.catch_id = e.source_id
          and (p.is_public or exists (select 1 from post_groups pg where pg.post_id = p.id and pg.group_id = $group))))
    or (e.source_type = 'challenge' and e.source_id in (select id from challenges where group_id = $group or scope = 'official')))
  where m.group_id = $group
  group by m.user_id
  order by xp desc
  ```
  All rows of one award key share a source, so plus and minus rows are included or excluded together.
- Positions: ties share a position (1, 2, 2, 4); zero-XP members listed last.
- Movement: table `ranking_seen` (`user_id`, `group_id`, `season_id`, `position`, `seen_at`); delta = last seen position − current; update after rendering.
- Caching: `unstable_cache` keyed by group and season, tag `ranking:<groupId>`; `CatchChanged` and `AudienceChanged` handlers revalidate the tags of the groups involved (after the response).
- UI: group page tab "Ranking": season label ("Temporada Out–Dez 2026"), `LeaderboardRow` list (podium discs 1–3, avatar, name, career title, XP in tabular figures, delta arrow with tooltip), my row in `water-soft` with "você", one line "Só contam peixes compartilhados com este grupo", season switcher (current and previous).
- i18n namespace `ranking`.

### Acceptance criteria
- [ ] Given Amanda shares a 200 XP catch with Group A only, then Group A's ranking includes it and Group B's doesn't.
- [ ] Given a public catch, then it counts in every group Amanda belongs to.
- [ ] Given two members with the same XP, then they share a position.
- [ ] Given I fell from 2nd to 3rd since my last visit, then my row shows "▼ 1" with the tooltip "Caiu 1".
- [ ] Given a removed member, then they're no longer in the ranking.

### Tests
- Integration: visibility scenarios (group-only, public, removed from group, audience changed); ties; seasons boundaries in Brasília time.
- E2E: part of J2 (ranking shows the new XP after logging).

## S-17 · See my rewards after logging a catch

**Type** Story · **Milestone** M2 · **Workstream** C · Social · **Priority** Must · **Size** M · **Journey** J2
**Depends on** {{S-13}}, {{S-14}}, {{S-15}}, {{S-16}} · **Blocks** {{S-42}}

### Story
As an angler who just logged a catch, I want to see what I earned, so that logging feels like a moment, not a form.

### Context
This is the demo's big moment. Build a calm static version first; S-42 adds the animation.

### Scope
- In: the reward screen, the ranking change, the promotion banner placement.
- Out: animation and the sea (S-42).

### Implementation notes
- After `logCatch` succeeds, go to `/log/done?c=<catchId>` with the `Rewards` from the response stored in `sessionStorage` (the page also works without it by reading the latest replay for that catch).
- Content, in order, each only if non-empty: new sticker (the `Sticker` component, "Figurinha nova!"), XP gained ("+175 XP") with the breakdown (catch, new species, new water type, milestone), promotion (`PromotionBanner`), ranking change per group ("Você subiu para 2º na Turma do Tietê").
- Ranking change: `gamification.rankingDelta(catchId)` computes, for each group that can see the catch, the angler's position with and without the XP rows of that replay (`replay_seq`). Fetched by the page after render so the screen appears immediately.
- No rewards (for example, a 7th catch of the day of a species already in the album): "Registrado! Esse já está no seu álbum." with a link to the album.
- Buttons: "Ver no feed", "Registrar outro".
- Tapping anywhere skips to the end state; everything is visible at rest.
- i18n namespace `rewards`.

### Acceptance criteria
- [ ] Given my first tucunaré, then the screen shows the sticker, "+175 XP" with its breakdown, and my new position in each group.
- [ ] Given I crossed a level, then the promotion banner shows here and not again in the feed.
- [ ] Given a repeat species, then the screen still confirms the catch and shows only the catch XP.
- [ ] Given a refresh of the page, then it still shows the same rewards.

### Tests
- Integration: `rankingDelta` with and without the replay's rows.
- E2E (J2 complete): log the first catch → reward screen with sticker and XP → album shows it → ranking shows the points.

## S-18 · Get notified about progress and rivals

**Type** Story · **Milestone** M2 · **Workstream** C · Social · **Priority** Must · **Size** M · **Journey** J2
**Depends on** {{S-13}}, {{S-16}} · **Blocks** {{S-30}}

### Story
As an angler, I want to know when I earn a sticker or level, or when someone passes me, so that I come back between trips.

### Context
Notifications are rows written by the module that reacts to an event, stored as a type plus data and rendered in the reader's language. "Overtaken" needs ranking math, so it runs right after the response instead of inside the save.

### Scope
- In: `notifications` table and module, the bell, the list page, sticker, level and overtaken types, polling.
- Out: social types (S-30), push (could-have).

### Implementation notes
- Table `notifications` (`notifications/schema.ts`): `id`, `recipient_id`, `type`, `actor_id` nullable, `subject_type`, `subject_id`, `data` jsonb, `created_at`, `read_at`. Index (`recipient_id`, `created_at desc`).
- `notifications.notify(tx, { recipientId, type, actorId?, subject, data })`.
- Types here: `sticker_new` (data: speciesId), `level_up` (data: level), `overtaken` (data: groupId, byUserId, newPosition).
- `sticker_new` and `level_up` are written by the `CatchChanged` handler from the `Rewards` (in the transaction).
- `overtaken`: `afterResponse` after `logCatch`/`updateCatch`; for each group that can see the catch, compare positions with and without this replay's rows; notify each member who was at or above the angler and is now below. At most one `overtaken` per recipient per group per day.
- Bell in the header with the unread count: `GET /api/notifications/unread` polled every 60 seconds while the tab is visible and on navigation.
- `/notifications`: list grouped by day; each type renders an i18n string with names and links ("Amanda passou você no ranking da Turma do Tietê"); opening the page marks all as read.
- Notifications older than 90 days are deleted by the daily job (S-27).
- i18n namespace `notifications`.

### Acceptance criteria
- [ ] Given Kauê logs a catch that moves him above me in our group, then I get one "overtaken" notification, in my language.
- [ ] Given he logs three more that day, then I still get only one for that group.
- [ ] Given I earn a sticker, then I see "Figurinha nova: Tucunaré-açu" in the list.
- [ ] Given I open the list, then the bell count goes to zero.

### Tests
- Unit: rendering of each type in both languages.
- Integration: overtaken computation and the daily throttle; unread count.

## S-19 · Earn milestone badges

**Type** Story · **Milestone** M2 · **Workstream** B · Gamification · **Priority** Should · **Size** S
**Depends on** {{S-13}} · **Blocks** nothing

### Story
As an angler, I want badges for firsts and milestones, so that small achievements get recognized too.

### Scope
- In: badge definitions, `user_badges`, the profile badge grid.
- Out: new milestone XP (the XP is already in S-13's `milestone` rule).

### Implementation notes
- `gamification/badges.ts`: ids matching the milestone rule (`first_catch`, `species_5`, `species_10`, `species_25`, `species_50`, `all_waters`), each with an icon name from the design system's Lucide set.
- Table `user_badges` (`user_id`, `badge_id`, `earned_at`, `source_catch_id`; PK on user and badge), rebuilt in `applyCatchChange` from the replay's milestone awards (a badge whose milestone is reversed is removed).
- Profile: badge grid, earned in color with the date, unearned greyed with the requirement.
- i18n `badges.<id>.name` and `.description`.

### Acceptance criteria
- [ ] Given my fifth species, then the "5 espécies" badge appears on my profile with today's date.
- [ ] Given I delete a catch so I'm back to four species, then the badge is removed.

### Tests
- Integration: badge earned and removed through replay.
