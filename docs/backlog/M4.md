## S-31 · Accept the terms and privacy notice

**Type** Story · **Milestone** M4 · **Workstream** A · Platform · **Priority** Must · **Size** S · **Labels** privacy
**Depends on** {{S-03}} · **Blocks** {{S-37}}

### Story
As a new user, I want to know what's collected and agree to it, so that I trust the app with my data.

### Context
Real people's data falls under Brazil's data protection law (LGPD). These texts are a good-faith summary written by the team, not legal advice; keep them short and plain.

### Implementation notes
- Content in `content/legal/terms.pt-BR.md`, `terms.en.md`, `privacy.pt-BR.md`, `privacy.en.md`, each with a version date at the top. Rendered at `/terms` and `/privacy` (public).
- Privacy notice covers: what's collected (email, name, handle, photo, home city, catches with optional exact location kept private, content you post, technical logs without personal data); why; who processes it (Supabase, Vercel, Anthropic for species ID on photos, Sentry, Resend); that photos are re-encoded and lose their metadata; retention; rights under the LGPD (access, correction, deletion via Settings); a contact email.
- Terms cover: be respectful, post your own photos, no illegal fishing content, we can remove content, the service is a beta.
- `profiles.terms_version` and `profiles.terms_accepted_at`. Onboarding adds a required checkbox linking both pages. If `TERMS_VERSION` in code is newer than the profile's, show a one-screen re-consent before app pages.
- Footer links on public pages and in Settings.

### Acceptance criteria
- [ ] Given onboarding without the checkbox, then it can't be completed.
- [ ] Given `TERMS_VERSION` bumped, then existing users see the re-consent screen once.
- [ ] Given `/privacy` signed out, then it renders in the browser's language.

### Tests
- Integration: consent stored with the version; re-consent gate.

## S-32 · Delete my account

**Type** Story · **Milestone** M4 · **Workstream** A · Platform · **Priority** Must · **Size** M · **Labels** privacy
**Depends on** {{S-13}}, {{S-21}}, {{S-28}} · **Blocks** {{S-37}}

### Story
As a user, I want to delete my account and data, so that I stay in control of what I shared.

### Context
Deletion removes everything tied to the person. The XP ledger is insert-only for the app account, so its rows go through a database cascade from the profile, which Postgres runs with the owner's permissions.

### Implementation notes
- Foreign keys from every user-owned table to `profiles(id)` with `on delete cascade`: catches, posts, comments, reactions, follows, group_members, xp_events, user_progress, album_entries, user_badges, notifications (as recipient), reports (as reporter), ranking_seen, media. `actor_id` in notifications and `moderation_actions` uses `on delete set null`.
- Command `identity.deleteAccount({ confirmHandle })` (tx): handle must match; for groups where the person is the only admin, promote the longest-standing member; collect media paths; delete the profile row (cascades); after commit, `afterResponse` deletes storage files (list kept in a `pending_deletions` table and retried by the daily job if it fails) and calls Supabase Auth admin `deleteUser`.
- Removing the person's reactions and comments must keep counters right: recompute `reaction_count` and `comment_count` for affected posts in the same transaction.
- UI `/settings/delete`: what will be deleted, type your handle to confirm, red button; afterwards sign out and show a goodbye page.

### Acceptance criteria
- [ ] Given a user with catches, posts, comments, reactions, XP and group admin roles, when they delete their account, then no row in any table references their id afterwards.
- [ ] Given their photos, then the storage files are gone within a day.
- [ ] Given other people's posts they had reacted to, then those counters are correct.
- [ ] Given they were the only admin of a group, then another member is admin now.

### Tests
- Integration: create a fully active user, delete, then query every table with a user-referencing column (from `information_schema`) and assert zero rows; counters correct; storage paths queued.

## S-33 · Rate limits and AI spending cap

**Type** Task · **Milestone** M4 · **Workstream** A · Platform · **Priority** Must · **Size** S
**Depends on** {{S-08}} · **Blocks** {{S-37}}

### Summary
Protect the app and the budget before real users arrive.

### Implementation notes
- `src/shared/rate-limit.ts`: `rateLimit(key, limit, windowSec)` with table `rate_limits` (`key`, `window_start`, `count`; PK on key and window): one `insert … on conflict do update set count = count + 1 returning count`; above the limit → `RATE_LIMITED`. Old windows deleted by the daily job.
- Limits per user (in one config file, `src/shared/limits.ts`): catches 20/day, posts and tips 30/day, comments 60/hour, reactions 300/hour, uploads 60/day, species ID 30/day, reports 20/day, follows 100/day, groups 5/day, join attempts 20/hour.
- AI cap: table `ai_usage` (`month`, `calls`, `alerted_80` bool). `species-id` increments `calls` in the same transaction as saving the result. `AI_MONTHLY_CALL_CAP` env; at 80% send one Discord message to `#alerts` through `DISCORD_ALERTS_WEBHOOK` and set `alerted_80`; at 100% identification returns `UNAVAILABLE` (the UI already falls back to manual pick).
- Manual: set a monthly spending limit in the Anthropic console; record it in `docs/reference/observability.md`.

### Acceptance criteria
- [ ] Given the 21st catch in a day, then it's refused with a message saying when it'll work again.
- [ ] Given `AI_MONTHLY_CALL_CAP=10` on Dev, then the 8th call posts one Discord alert and the 11th falls back to manual pick.

### Tests
- Unit: limits config shape.
- Integration: window rollover; parallel hits never exceed the limit by more than one; AI cap behavior with the model mocked.

## S-36 · First-run experience and empty states

**Type** Story · **Milestone** M4 · **Workstream** C · Social · **Priority** Must · **Size** M · **Journey** J1
**Depends on** {{S-05}}, {{S-14}}, {{S-16}} · **Blocks** {{S-37}}

### Story
As someone opening the app for the first time, I want to understand what to do, so that I log my first catch.

### Implementation notes
- After onboarding without a pending invite: a screen with two choices, "Criar um grupo" and "Tenho um código de convite" (code input → S-05).
- Empty states, each with one sentence and one action:
  - Feed, no groups: create or join.
  - Group feed, no posts: "Registre o primeiro peixe da turma."
  - Album, nothing filled: "Sua primeira captura cola a primeira figurinha."
  - Ranking, season just started: "A temporada começou. Quem pontua primeiro?"
  - Challenges, none: admins see "Criar desafio"; members see "Peça um desafio para o admin".
  - Notifications: "Nada por aqui ainda."
- A static illustration of the sea (from the design system's palette) on empty states; the animated version is S-42.
- A first-catch hint on the Log button (one-time pulse, respects reduced motion).

### Acceptance criteria
- [ ] Given a brand-new user with no invite, then they reach a group and the log form in two taps.
- [ ] Given every listed screen with no data, then it shows its message and action instead of a blank area.

### Tests
- E2E: new user with no invite creates a group and opens the log form; screenshot each empty state on mobile.

## S-37 · Beta release and invite outside groups

**Type** Task · **Milestone** M4 · **Workstream** All · **Priority** Must · **Size** M
**Depends on** {{S-31}}, {{S-32}}, {{S-33}}, {{S-34}}, {{S-36}} and all M1–M3 Musts · **Blocks** {{S-35}} numbers, {{S-45}}

### Summary
Release `dev → main`, bring in the 2–3 outside groups, and listen.

### Implementation notes
- Pre-release checklist (in the release PR):
  - Production environment variables complete (compare with `.env.example`).
  - Google OAuth redirect URIs include production; Resend domain verified, or email sign-up hidden and Google only.
  - Catalog seeded in production; no demo data in production.
  - `#alerts` receiving; uptime green; Healthchecks check active.
  - Full Playwright suite green on the release PR.
- Feedback: a "Enviar feedback" item in the profile menu with a short form (text, optional screenshot) saved to a `feedback` table and posted to a Discord `#feedback` channel through a webhook.
- Invite message template for group captains (Portuguese), with what the app is, that it's a beta, and the invite link.
- Daily triage (15 minutes, rotating owner): Sentry issues, `#feedback`, Healthchecks, new board items for anything real.

### Acceptance criteria
- [ ] Given the release, then production serves the release commit and `/api/health` is green.
- [ ] Given the first outside group, then at least one of its members has joined and logged a catch.
- [ ] Given a week of beta, then no Sentry issue in `#alerts` stays unacknowledged for more than a day.
